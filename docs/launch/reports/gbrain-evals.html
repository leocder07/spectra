Architecture (13)

high Adapter interface contract violated by agent adapter ~4.0h ▶
eval/runner/adapters/claude-sonnet-with-tools.ts:145-153
ClaudeSonnetWithToolsAdapter implements the Adapter interface but its query() method throws unconditionally. This is a Liskov Substitution violation — any code iterating over adapters generically (e.g., multi-adapter dispatch) must special-case this adapter. The interface should be split into RetrievalAdapter and AgentAdapter, or expressed via a discriminated union/optional capability flag, so consumers cannot accidentally call query() on an agent adapter.
Recommendation: Introduce two interfaces: RetrievalAdapter (with query) and AgentAdapter (with runAgentLoop). Have ClaudeSonnetWithToolsAdapter implement only AgentAdapter. Update types.ts to export both, and let runners select by capability rather than using a single Adapter type.
medium Adapter init() signature inconsistent across adapters (poisonFixtures only on agent adapter) ~3.0h ▶
eval/runner/adapters/claude-sonnet-with-tools.ts:130-130
ClaudeSonnetWithToolsAdapter.init() widens the AdapterConfig with `& { poisonFixtures?: PoisonFixture[] }`, while RipgrepBm25Adapter and HybridNoGraphAdapter use their own narrowed config types. This breaks the pluggability story: a generic dispatcher cannot pass a single config blob to all adapters without each adapter understanding extra fields. The shared types contract in types.ts does not document this extension model.
Recommendation: Define AdapterConfig in types.ts as an open-ended record with a typed `extensions` field, or use per-adapter config generics on the Adapter interface (Adapter<TConfig extends AdapterConfig>). Document the contract in types.ts so all adapters surface required config consistently.
medium Optional adapter lifecycle methods (snapshot, teardown) inconsistently implemented ~2.0h ▶
eval/runner/adapters/claude-sonnet-with-tools.ts:156-163
RipgrepBm25Adapter implements snapshot() but not teardown(); HybridNoGraphAdapter implements teardown() but not snapshot(); VectorOnlyAdapter implements snapshot() but not teardown(); ClaudeSonnetWithToolsAdapter implements teardown() with an `as any` cast on engine.disconnect. This produces resource leaks (PGLite engines not always disconnected) and inconsistent reproducibility across runs.
Recommendation: Make teardown() mandatory in the Adapter interface (returning Promise<void>; default no-op for in-memory adapters). Add snapshot() as a separately-typed optional capability. Remove the `as any` cast by typing PGLiteEngine.disconnect properly in the engine import.
medium BrainState as opaque `any`-equivalent loses type safety across adapter boundary ~3.0h ▶
eval/runner/types.ts
Each adapter casts BrainState to its concrete state type at the top of query() (e.g., `state as Bm25State`, `state as VectorOnlyState`, `state as HybridNoGraphState`). This is the classic `void*` anti-pattern: BrainState carries no compile-time guarantee that the state passed to query() is the one returned by init(). A wiring bug between init/query in multi-adapter.ts would compile cleanly and crash at runtime.
Recommendation: Make Adapter generic in its state type: `interface Adapter<S = unknown> { init(...): Promise<S>; query(q, state: S): Promise<RankedDoc[]>; teardown?(state: S): Promise<void> }`. Each adapter then declares its concrete S, and the compiler enforces init/query state agreement.

eval/runner/all.ts:60-130
all.ts dispatches Cats 1-4, 6, 7, 10-12 as subprocesses and skips Cats 5, 8, 9 because they require runtime inputs. The discriminated union (SubprocessCategory | ProgrammaticCategory) is fine, but there is no single entry point that runs everything — the report just notes 'run via harness'. Security (8)

medium Command injection risk in browser open via execSync with file path ~0.5h ▶
eval/cli/world-view.ts:24-26
In world-view.ts, the path returned from renderWorldHtmlToFile is interpolated directly into a shell command via execSync(`${cmd} "${path}"`). While the path is derived from a --dir argument (default constant), a user-supplied --dir could contain shell metacharacters (e.g., `"; rm -rf ~`) producing command injection. CWE-78: OS Command Injection. Even though the tool is a developer convenience, accepting CLI args and shelling out unquoted-safely is a code-injection sink.
Recommendation: Use execFile(cmd, [path]) instead of execSync with string interpolation, which passes path as a separate argv and avoids shell parsing. Alternatively, validate that the resolved path contains no shell metacharacters before invoking execSync.
medium pdf-parse dependency: known historical RCE/parsing vulnerabilities ~4.0h ▶
package.json:28-30
package.json lists pdf-parse@^2.4.5 as a devDependency for the PDF loader. The pdf-parse ecosystem (and underlying pdfjs-dist) has had multiple CVEs related to malicious PDF parsing leading to memory issues / prototype pollution. Since adversarial PDFs are explicitly part of this benchmark, parsing untrusted PDFs in the same process as Anthropic API keys is a real concern. CWE-1395: Dependency on Vulnerable Third-Party Component.
Recommendation: Pin pdf-parse to the latest patched version, run `bun audit` / npm audit in CI, and isolate PDF parsing behind a worker process with no env access. Consider running adversarial PDF ingestion under a separate user / container with no API keys mounted.

medium VectorOnlyAdapter scores cosine over every doc on every query (O(N×D) full scan) ~3.0h ▶

query() iterates `s.vectors` (size N) and computes cosine against every page vector — a full O(N×D) scan on each call. For the 240-page corpus this is ~240×3072 = 737K float ops per query (fast), but if the corpus or query set grows (e.g., Cat 6 prose-scale runs 500+ pages with N=10 reruns = 5000+ queries), latency scales linearly. Also, the cosine loop is per-element JS — no SIMD, no normalized-vector dot-product fast path.
Recommendation: Pre-normalize stored vectors to unit length at init time so query reduces to a dot product (drop two of the three sqrt/div ops).
