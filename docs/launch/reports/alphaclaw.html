Architecture (9)

high Monolithic App component with excessive route-specific knowledge ~12.0h ▶
lib/public/js/app.js:64-95
lib/public/js/app.js acts as a god component: it owns location parsing for /agents, /chat, /cron, /envars, /models, /nodes, manually checks isXRoute booleans, extracts selectedAgentId/selectedCronJobId via regex, and mounts route components conditionally outside the Switch. This bypasses wouter-preact's routing for most routes, duplicates routing logic, and creates a tight coupling between the shell and every feature. Adding a new route requires editing this 400+ line file in multiple places (booleans, regex parsers, JSX branches, sidebar handlers).
Recommendation: Move all route mounting into the <Switch> with <Route> declarations and use route params (via wouter useParams) instead of regex parsing of location. Extract sidebar wiring into a separate AppShell component and let each route component own its own pane wrapper class.
high Inconsistent routing strategy: hand-rolled conditionals bypass Switch/Route ~8.0h ▶
lib/public/js/app.js:217-295
Some routes (/general, /doctor, /telegram, /usage, /webhooks, /watchdog) are declared inside <Switch> with proper <Route> elements, while /agents, /chat, /cron, /envars, /models, /nodes are mounted via plain conditional rendering using location.startsWith(). This dual routing model means route precedence, fallthrough, and the catch-all <RouteRedirect to="/general"> behave unpredictably, and the lib/public/js/components/routes/index.js barrel exports become inconsistently used.
Recommendation: Pick one routing strategy (recommend wouter <Switch>/<Route>) and migrate all panes into it. The barrel in components/routes/index.js already exports route components — use them uniformly inside the Switch.
medium Cross-cutting global window state and DOM events used as control plane ~4.0h ▶
lib/public/js/app.js:121-130
The shell uses window['__alphaclawPendingCreateAgent'] as a flag to coordinate navigation→action handoff, dispatches CustomEvents on window ('alphaclaw:create-agent'), and listens for them in components/agents-tab/index.js. This is an ad-hoc pub/sub bypassing the component tree, making data flow opaque and racy. Window globals also pollute the namespace ('__alphaclawSetupAppBootCount').
Recommendation: Replace window-flag + window.dispatchEvent with explicit prop callbacks or a small typed event bus / context. Pass an onRequestCreateAgent prop down to AgentsRoute and trigger the modal via state, removing the need for cross-tree DOM events.
medium Plugin tightly coupled to undocumented core event names and ctx shape ~4.0h ▶
lib/plugin/usage-tracker/index.js:168-200
lib/plugin/usage-tracker/index.js subscribes to 'llm_output' and 'tool_result_persist' events with hand-coded shapes for event.usage.{input,output,cacheRead,cacheWrite,total} and ctx.{sessionId,sessionKey,toolName}. There is no shared schema/contract module visible — the plugin will silently break (writes 0) if the host changes field names. This violates the typical plugin-architecture contract of stable, documented hooks.
Recommendation: Define the plugin API surface in a shared module (e.g. lib/server/plugin-api/contracts.js) exporting event name constants, event shape validators, and version. Have the plugin import constants instead of hardcoding strings, and version-check the api object on register.
medium Plugin opens its own SQLite DB and resolves config out-of-band ~3.0h ▶
lib/plugin/usage-tracker/index.js:14-19
The usage-tracker plugin independently resolves the install root from process.env (ALPHACLAW_ROOT_DIR / OPENCLAW_HOME / OPENCLAW_ROOT_DIR / homedir fallback) and opens its own SQLite file. The host server presumably already knows the config root and may manage other DBs. Each plugin reinventing path resolution leads to inconsistencies (which env wins?) and bypasses any centralized DB lifecycle (close on shutdown, migrations, backup).
Recommendation: Have the host pass an api.paths.dataDir (or api.openDatabase('usage')) to plugin.register() so plugins do not duplicate environment resolution. Centralize DB connection lifecycle in the host so close()/WAL checkpointing happens on shutdown.
medium No DB connection close / lifecycle hook in plugin ~2.0h ▶
lib/plugin/usage-tracker/index.js:152-200
The plugin lazily opens DatabaseSync on first event but never exposes an unregister/close hook. On server reload or shutdown the WAL file may not checkpoint cleanly, prepared statements leak, and tests cannot tear down the plugin between runs. The plugin contract appears to expose only register(api) with no symmetric dispose.
Recommendation: Extend the plugin contract to support an optional unregister/dispose function that closes prepared statements and the DatabaseSync handle. Have the host call it during shutdown.

Security (2)

medium OAuth popup auth URL constructed without verifying same-origin postMessage source ~1.0h ▶
lib/public/js/components/google/index.js
In lib/public/js/components/google/index.js the message handler accepts event.data.google === 'success'/'error' from any window without checking event.origin. Although same-origin policy makes injecting messages from cross-origin frames difficult, it is best practice to verify origin to prevent confused-deputy issues if a malicious page is opened in the same browser context. CWE-346: Origin Validation Error.
Recommendation: In the window 'message' event handler, add: if (event.origin !== window.location.origin) return; before processing event.data. Also validate that event.source matches the popup window reference returned by window.open.

This is informational only — pattern is safe as written but worth flagging because future maintainers might add interpolation. CWE-89 (not currently exploitable).
Recommendation: Add a comment indicating these schema strings must remain literal. Continue using prepared statements (already done correctly via database.prepare with $named parameters) for all dynamic queries.

Performance (8)

high Synchronous SQLite writes in usage-tracker block event loop on every LLM/tool event ~6.0h ▶
lib/plugin/usage-tracker/index.js:174-213
writeUsageEvent() and writeToolEvent() use DatabaseSync (node:sqlite synchronous binding) on the hot path of every llm_output and tool_result_persist event. Each LLM completion triggers two sequential synchronous writes (insertUsageEventStmt.run + upsertUsageDailyStmt.run) which block the Node.js event loop. Under high agent throughput (multiple concurrent sessions, frequent tool calls), this can stall HTTP/WebSocket handling. There is no batching or write-behind buffer.
Recommendation: Either (a) wrap the two writes in a single transaction (BEGIN/COMMIT) to halve the fsync cost; (b) batch events in memory and flush every N ms / N events; or (c) move writes to a worker_thread. Given WAL+synchronous=NORMAL is already set, batching transactions of ~50 events would be the highest-impact fix.
medium tool_events table missing index on timestamp ~0.5h ▶
lib/plugin/usage-tracker/index.js:78-99
The tool_events table has indexes on session_id and session_key but none on timestamp. Any analytics query filtering by time range (e.g., 'tool calls in last 24h') will require a full table scan. With high-volume tool usage this grows unbounded, causing read latency to climb linearly with row count.
Recommendation: Add `CREATE INDEX IF NOT EXISTS idx_tool_events_ts ON tool_events(timestamp DESC);` mirroring the usage_events index. Also consider a composite (session_key, timestamp) index for per-session timeline queries.
low Polling pattern triggers redundant fetches across many components ~8.0h ✓ validated ▶
lib/public/js/components/doctor/index.js:50-86
The DoctorTab uses three independent usePolling hooks (status, runs, cards) all polling at 2s when a run is in progress. Combined with similar patterns across general/watchdog/cron/usage tabs, this generates substantial network traffic. Each polling instance independently triggers HTTP roundtrips with no shared coalescing. With 5+ active panels polling every 2s, that's 150+ requests/minute just from one user.
Recommendation: Consider replacing aggressive 2s polling during active runs with SSE/WebSocket push updates (an sse.js client already exists). At minimum, share an api-cache layer so the three doctor polls don't issue redundant fetches when overlapping. Also gate polling behind document.visibilityState so background tabs don't keep polling.
