Architecture (10)

high CLI dispatcher is a god-function with hardcoded command registry ~8.0h ▶
src/cli.ts:22-22
src/cli.ts contains a 60+ entry CLI_ONLY Set and a giant switch/if-else chain in handleCliOnly that hardcodes every command name and its dynamic import path. Adding a command requires touching 3+ places (CLI_ONLY set, handleCliOnly switch, help text). This violates open-closed principle and is the single largest architectural debt in the dispatch layer — operations are otherwise discoverable via the operations registry, but CLI-only commands aren't.
Recommendation: Introduce a command registry pattern: each command module exports a CommandSpec { name, needsEngine, handler, help } and a barrel file aggregates them. Replace the switch with a Map lookup, mirroring the existing operations registry pattern. This eliminates the CLI_ONLY Set and the duplicated import boilerplate.
high Command layer reaches into MCP transport (cross-layer dependency) ~2.0h ▶
src/commands/call.ts:2-2
src/commands/call.ts imports handleToolCall from '../mcp/server.ts'. This inverts the expected layering: commands should depend on core (operations, engine), not on a transport adapter. The MCP server should depend on operations, and `gbrain call` should also dispatch through operations directly — not through the MCP server module. This creates a circular concern where mcp/ and commands/ are peers but commands/ pulls from mcp/.
Recommendation: Refactor `gbrain call` to import dispatchToolCall from src/mcp/dispatch.ts (or better: a renamed src/core/dispatch.ts since dispatch is transport-agnostic). Move dispatch.ts under src/core/ since it's used by both transport adapters and CLI commands.
high Auth command bypasses engine abstraction with raw postgres driver ~3.0h ▶
src/commands/auth.ts:17-17
src/commands/auth.ts imports `postgres` directly and uses raw SQL via the postgres tagged template, completely bypassing BrainEngine. This means: (a) the command will not work with PGLite brains despite the rest of the system supporting both engines, (b) it duplicates connection/config logic (DATABASE_URL handling) that loadConfig() + engine-factory already solve, and (c) it violates the single point of DB access enforced elsewhere.
Recommendation: Refactor auth.ts to receive a BrainEngine and use engine.executeRaw() for the access_tokens CRUD. Either route through cli.ts's connectEngine() or expose a thin AuthRepository in core/ that both engines implement. Remove the direct postgres import.
medium MCP server imports core operations directly, bypassing a transport boundary ~2.0h ▶
src/mcp/server.ts:32-47
src/mcp/server.ts imports `operations` from '../core/operations.ts' and the dispatch helpers from './dispatch.ts'. The 'backward compat' handleToolCall in server.ts duplicates dispatch logic (validateParams + buildOperationContext + op.handler) that already exists in dispatch.ts. This couples the MCP transport to operation internals and creates two code paths for tool invocation (`gbrain call` vs MCP stdio) that can drift.
Recommendation: Collapse handleToolCall into a single call to dispatchToolCall with { remote: false }. The MCP server should only know about transport (stdio, HTTP) and delegate ALL execution to dispatch.ts. Move operations import out of server.ts entirely.
medium Autopilot reaches into engine internals via 'as any' casts ~4.0h ▶
src/commands/autopilot.ts
autopilot.ts contains multiple `(engine as any).executeRaw?.(...)` and `(engine as any).connect?.()` calls (lines around the no-worker probe and reconnect block). This bypasses the type system and signals that BrainEngine's interface is incomplete — callers know methods exist but the type doesn't expose them. Coupled with the engine-parity finding, this is evidence that BrainEngine is under-specified as a port.
Recommendation: Audit BrainEngine type and add executeRaw, connect, getConfig, getHealth, getCallersOf, getCalleesOf as first-class methods on the interface. Eliminate `as any` casts in command-layer code. If a method is genuinely engine-specific, narrow the type with a discriminated union or keep it private.
medium Operation result formatting hardcoded into CLI with type assertions ~6.0h ▶
src/cli.ts:156-230
formatResult() in cli.ts contains a switch with cases for get_page, list_pages, search, query, get_tags, get_stats, get_health, get_timeline, get_versions — each casting result to `any` and reaching into ad-hoc shapes. This couples the CLI to operation result internals without a type contract. New operations require editing this switch; renaming a result field silently breaks formatting.
Recommendation: Move per-operation formatting into the operation definition itself (e.g., op.cliHints.format?: (result) => string). The CLI then becomes a generic dispatcher: `const out = op.cliHints?.format?.(result) ?? JSON.stringify(result, null, 2)`. This co-locates result shape and presentation, eliminating the god-switch.

Security (7)

low Auth `test` subcommand argument parsing flaw allows token leak via process listing ~1.5h ▶
src/commands/auth.ts:245-252
In `runAuth`, the `test` subcommand parses `--token` by index, but the URL detection `rest.find(a => !a.startsWith('--') && a !== rest[tokenIdx + 1])` may misidentify the URL when arguments are reordered, potentially passing the token as URL or vice versa. More importantly, tokens supplied on the command line are visible to other users via `ps`/`/proc`. CWE-214: Invocation of Process Using Visible Sensitive Information.
Recommendation: Read the token from an environment variable (e.g., GBRAIN_TOKEN) or stdin instead of a CLI flag, and warn users that --token may leak via process tables. Also tighten arg parsing to deterministically identify the URL positional.
low Token created without expiration / rotation policy ~3.0h ▶
src/commands/auth.ts:41-49
`access_tokens` rows have `created_at` and `revoked_at` but no expiration timestamp. Long-lived bearer tokens that never auto-expire elevate the blast radius of any leak. CWE-613: Insufficient Session Expiration. OWASP A07:2021.
Recommendation: Add an `expires_at` column with a sensible default (e.g., 90 days), enforce it in the auth-validation path, and surface remaining lifetime in `auth list`. Consider supporting rotation via `auth rotate <name>`.
low Lock file race between stat and write in autopilot ~1.5h ▶
src/commands/autopilot.ts
The autopilot lock-file logic does a stat-then-write without atomic exclusivity. Two concurrent `gbrain autopilot` invocations can both pass the freshness check and both write their PID, defeating mutual exclusion. CWE-367: TOCTOU Race Condition.
Recommendation: Use `fs.openSync(lockPath, 'wx')` (exclusive create) or a real OS file lock (`flock`/`lockfile-utils`). On EEXIST, check mtime to detect stale locks then delete-and-retry once.
low Unbounded JSON parse on user-supplied tool args (`gbrain call`) ~1.5h ▶
src/commands/call.ts:13-14
`runCall` calls `JSON.parse(jsonStr)` directly on argv with no size cap, schema check, or prototype-pollution guard. A maliciously crafted argument like `'{"__proto__":{"polluted":true}}'` mutates Object.prototype globally for the process. CWE-1321: Prototype Pollution. CWE-20: Improper Input Validation.
Recommendation: Use a safe parser (e.g., `JSON.parse` with a reviver that drops `__proto__`/`constructor`/`prototype` keys) or schema-validate against the operation's `params` definition before passing to the handler. Cap argv length (e.g., 1MB).
low MCP stdio handler trusts caller-supplied params without rate limiting ~3.0h ▶
src/mcp/server.ts:22-32
`startMcpServer` dispatches every CallToolRequest with `remote: true` but applies no per-session rate limit, concurrency cap, or payload-size limit at the stdio layer. A misbehaving MCP client can flood the dispatcher and exhaust DB connections. CWE-770: Allocation of Resources Without Limits or Throttling.
Recommendation: Add a minimal in-process token bucket (e.g., 50 req/s per session) and enforce a max param-payload size in `dispatchToolCall`. Even stdio clients can be misconfigured loops.

high Pervasive use of 'any' type undermines TypeScript strictness ~8.0h ▶
src/cli.ts:153-244
Despite TypeScript usage, the codebase contains numerous `as any` casts and `: any` type annotations in critical paths (cli.ts formatResult, mcp/server.ts request handlers, autopilot.ts engine probes, auth.ts error handling). Recommendation: Define explicit result types for each operation (GetPageResult, ListPagesResult, etc.) and replace `as any` casts with proper type narrowing. For MCP SDK width issues, create a local typed interface rather than casting to any.
