Architecture (9)

high Module boundary violation: browse CLI imports host config via dynamic absolute path ~4.0h ▶
browse/src/cli.ts:478-487
browse/src/cli.ts dynamically imports hosts/index.ts using path.resolve(__dirname, '..', '..', 'hosts', 'index.ts'). This creates a hidden cross-module dependency from the browse subsystem (which compiles to a standalone binary) into the hosts/ registry. It bypasses the module system, breaks in compiled binaries (where __dirname points into $bunfs), silently falls back to a hardcoded convention path on failure, and couples browse to the gstack monorepo layout. The browse binary should be self-contained per its design as a 'persistent Chromium daemon'.
Recommendation: Either (a) extract host globalRoot resolution into a small data file (e.g., hosts/globals.json) that browse can read, (b) accept the globalRoot as a CLI argument from the calling skill, or (c) move the --local pair-agent flow into a separate gstack-level CLI that legitimately depends on hosts/. The current dynamic path import is an architectural shortcut that defeats the binary's portability.

browse/src/browser-manager.ts
BrowserManager in browser-manager.ts is a classic god object. It owns: lifecycle (launch/close/handoff), tab management, ownership/multi-agent isolation, dialog handling, cookie tracking, viewport/UA, watch mode, ref maps, snapshot diffing, frame context, two-tier CDP mutex, headed mode patches, anti-bot stealth scripts, plist patching, icon copying, and SSE-style disconnect callbacks. Security (7)

high Auth token leaked via /health endpoint without origin restriction ~4.0h ▶
browse/src/server.ts
The /health endpoint returns the daemon's root AUTH_TOKEN unconditionally when in headed mode, and to any caller whose Origin header starts with 'chrome-extension://'. The Origin header is client-controlled in non-browser contexts (curl, fetch from any process on the host), and any local process on 127.0.0.1 can read it. Comments in the code acknowledge this as 'a separate concern (v1.1+ TODO)'. A malicious local process or compromised browser extension could fetch the token and gain root capability over the daemon, including ability to mint scoped tokens, run JS in arbitrary tabs, read cookies, etc. CWE-522: Insufficiently Protected Credentials. OWASP A07:2021.
Recommendation: Remove the token from /health entirely. Use a separate authenticated bootstrap endpoint that requires either a one-time exchange code (similar to setup_key flow) or a filesystem-protected handoff (read token from ~/.gstack/.auth.json with 0600 perms, which the code already writes). Origin header is not a security boundary against local processes.
medium Telemetry-ingest accepts arbitrary installation_id without authentication or rate limiting ~6.0h ▶
supabase/functions/telemetry-ingest/index.ts
The Supabase telemetry-ingest edge function accepts events with client-supplied installation_id (up to 64 chars), gstack_version, os, and writes them via the anon key. There is no authentication, no per-installation rate limit, and no signature verification. An attacker can poison the telemetry table at scale, inflate weekly_active counts, manipulate top_skills/top_versions in /community-pulse, or spam crash_clusters. The 50KB/100-event-per-batch caps only slow this. CWE-345: Insufficient Verification of Data Authenticity. CWE-770: Allocation of Resources Without Limits.
Recommendation: Add a per-IP rate limit (e.g. 100 events/min) via Supabase rate limiting or an edge proxy. Consider HMAC-signed events using a key the gstack client derives from installation_id (still defeatable but raises bar). At minimum, log source IP for forensic analysis and add a CAPTCHA-like proof-of-work for high-volume submitters.
medium PTY session token transmitted in JSON response body in addition to HttpOnly cookie ~4.0h ▶
browse/src/pty-session-cookie.ts
The /pty-session endpoint returns the freshly-minted ptySessionToken in the JSON response body so the extension can pass it via Sec-WebSocket-Protocol. The code's own comment acknowledges this is required because browsers don't allow custom headers on WebSocket from JS. However, this means the token sits in JS-accessible memory in the page that called fetch() — defeating the HttpOnly protection of the parallel cookie. Any XSS in the extension UI page (sidepanel) would be able to exfiltrate the token. CWE-522.
Recommendation: The current design accepts this trade-off explicitly. Mitigations: (1) Ensure Sidebar UI has strict CSP with no inline scripts and no unsafe-eval. (2) Keep the 30-min token TTL short (already done). (3) Verify the WebSocket upgrade also validates a per-connection challenge so a stolen token alone is not enough. (4) Document the threat model clearly so future changes don't widen the surface.
low Insufficient lock file content validation (TOCTOU on lock file PID parsing) ~3.0h ▶
browse/src/cli.ts
acquireServerLock() in cli.ts reads the lock file, parseInts the contents, and checks if the PID is alive. An attacker (or a colliding test) could write a fake PID matching an unrelated alive process (e.g., pid 1) into the lock file, and the lock would be considered held forever, blocking server startup. Inverse: a stale lock could be removed and concurrent starts could race. CWE-367: TOCTOU Race Condition.
Recommendation: Use fcntl/flock-style advisory locks where available, or include a lock file timestamp + content signature so a stale lock is detected by age. The wx flag handles the basic atomic create case but the recovery path (read PID + recreate) is racy.
low Activity stream filterArgs may miss password fields with non-standard names ~1.5h ▶
browse/src/activity.ts
filterArgs() in activity.ts redacts fill values when the selector matches /password|passwd|secret|token/i. Sites using 'pin', 'pwd', 'auth-code', '2fa', 'otp', 'mfa' or non-English language fields (e.g., 'mot-de-passe') will leak credentials to the activity stream. The activity stream is exposed via SSE to any holder of the SSE session cookie (which is bound to root token bootstrap, so risk is bounded but the data is still persisted in the in-memory ring buffer). CWE-200: Exposure of Sensitive Information.
Recommendation: Expand the regex to cover common credential field names: /password|passwd|pwd|secret|token|pin|otp|mfa|2fa|auth.?code|cvv|ssn|social/i. Better: redact ALL fill values by default and only allow plain values when the selector explicitly matches a known-safe pattern (e.g., 'search', 'query', 'comment'). Defense in depth: also match by input type=password attribute via pre-fill metadata.
low Skill spawn token TTL not enforced against orphaned tokens on crash ~2.0h ▶
browse/src/browser-skill-commands.ts
spawnSkill() mints a scoped token via mintSkillToken, then in finally{} calls revokeSkillToken. If the parent process is SIGKILLed mid-spawn, the token registry's in-memory state may be lost but if it's persisted (token-registry.ts handles serialization), the token could outlive the spawn. Performance (5)

high Unbounded response body buffering for network capture ~1.5h ▶
browse/src/browser-manager.ts
In browser-manager.ts wirePageEvents(), every requestfinished event calls `await res.body()` which loads the full response body into memory just to compute its byte length. For pages that download large assets (videos, PDFs, large JSON), this allocates the full payload (potentially hundreds of MB) per request only to discard it. With BROWSE_HEADED, the user can navigate to anything — a single video stream can OOM the daemon.
Recommendation: Use the Content-Length response header when present, or fall back to a size cap (e.g., skip body() for responses where headers indicate >1MB; or read response.headers()['content-length']). Never download the body solely to count bytes.
medium Synchronous fs.appendFileSync blocks event loop on every flush ~1.0h ▶
browse/src/server.ts
flushBuffers() runs every 1 second and uses fs.appendFileSync three times (console, network, dialog logs). With 50,000-entry CircularBuffers, each flush can serialize and write large blocks synchronously, blocking the Bun event loop and stalling all in-flight HTTP commands during the write. The 'async' marker on flushBuffers() is misleading — there are no awaits.
Recommendation: Replace fs.appendFileSync with fs.promises.appendFile (or Bun.write with append). The flushInProgress guard already prevents concurrent flushes, so an async write is safe. This removes the 1-Hz event-loop stall under heavy logging.
medium Activity buffer toArray() copies 1000 entries on every getActivityAfter() ~2.0h ▶
browse/src/activity.ts
getActivityAfter() in activity.ts calls activityBuffer.toArray() (allocates a 1000-element array) then filters it with a linear scan. Every SSE client connection and every poll triggers this. Multiple sidebar/extension clients amplify the cost. Since entries are inserted with monotonic IDs, a binary search on the ring buffer would suffice.
Recommendation: Add a method to CircularBuffer that returns entries with id > afterId without materializing the full array — binary search the head-relative position, then iterate from there. Alternatively, only materialize the slice past afterId.
