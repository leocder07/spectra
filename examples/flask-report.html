medium God class tendency in Flask app.py ~40.0h ▶
src/flask/app.py:1
The `Flask` class in `src/flask/app.py` inherits from `sansio/app.py::App` which itself inherits from `Scaffold`. Together these form a very large class surface area. The `Flask` class handles WSGI dispatching, context management, request/response processing, error handling, server running, CLI integration, and more. While the sansio split helps, the combined class still has an enormous number of methods and responsibilities. The `App` base in sansio likely contains routing, config, URL rules, template configuration, error handler registration, and blueprint registration — all in one class.
Recommendation: This is somewhat inherent to Flask's design philosophy of simplicity. For a framework of this maturity, this is acceptable but worth noting. Consider whether any further decomposition (e.g., extracting a RequestDispatcher or ContextManager mixin) would improve maintainability without breaking the public API.
low Context management architecture is well-structured but tightly coupled ~8.0h ▶
src/flask/ctx.py:1
The context system in `src/flask/ctx.py` implements `AppContext` and `RequestContext` as separate classes with proper push/pop lifecycle management. The `globals.py` module provides proxy objects (`current_app`, `request`, `session`, `g`) using Werkzeug's `LocalProxy` and `LocalStack`. However, the context pushing/popping logic in `ctx.py` is tightly coupled to the `Flask` app class — `RequestContext` directly references and manipulates the app's `_got_first_request` flag and calls `app.ensure_sync()` for teardown functions. This coupling makes it difficult to test context behavior independently.
Recommendation: Consider defining a minimal interface/protocol that contexts expect from the app object, rather than depending on the full Flask class. This would improve testability and make the context system more self-contained.

Security (6)

high No runtime warning when SECRET_KEY is default or weak ~4.0h ▶
src/flask/config.py
Flask's session signing depends entirely on SECRET_KEY, but the framework does not validate the strength of the key at runtime. If a developer sets a weak or short SECRET_KEY, session cookies can be brute-forced. The config.py module loads SECRET_KEY without any entropy or length checks. CWE-326: Inadequate Encryption Strength. OWASP A02:2021 Cryptographic Failures.
Recommendation: Add a runtime warning (not error, to avoid breaking changes) when SECRET_KEY is set to a value shorter than a recommended minimum (e.g., 16 bytes of entropy) and the application is not in debug mode. Flask already warns about missing SECRET_KEY in some paths, but strength validation would improve security posture.
medium SecureCookieSessionInterface does not set Secure flag by default ~4.0h ▶
src/flask/sessions.py
In src/flask/sessions.py, the SecureCookieSessionInterface.get_cookie_attrs() method sets the 'secure' cookie attribute based on SESSION_COOKIE_SECURE config, which defaults to False. This means session cookies are transmitted over unencrypted HTTP by default, exposing them to network-level interception. CWE-614: Sensitive Cookie in HTTPS Session Without 'Secure' Attribute. OWASP A02:2021 Cryptographic Failures.
Recommendation: This is a framework design choice for development convenience, but consider documenting more prominently that SESSION_COOKIE_SECURE should be True in production. Consider adding a warning when DEBUG=False and SESSION_COOKIE_SECURE is not set.
