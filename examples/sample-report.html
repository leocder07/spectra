Architecture (9)

medium Prototype augmentation pattern for request/response creates implicit coupling
lib/request.js
lib/express.js creates the app by generating a plain function, then mixes in application.js methods via mixin(). It also sets req and res prototypes that inherit from Node's http.IncomingMessage and http.ServerResponse respectively. This monkey-patching approach (augmenting native prototypes with custom properties) creates tight coupling between Express internals and Node.js HTTP objects. While this is a deliberate and long-standing design choice, it means request.js and response.js cannot be understood in isolation — they depend on runtime prototype chain setup performed in express.js and on properties set during request handling in application.js.
Recommendation: This is a fundamental design decision of Express that enables its lightweight feel. For a next-generation rewrite, consider composition over inheritance (wrapping rather than extending native objects). For the current codebase, document the prototype chain setup clearly.
medium Response module likely has bidirectional awareness with application settings
lib/response.js
lib/response.js needs access to application-level settings (e.g., 'json spaces', 'etag', 'json escape', 'jsonp callback name') to implement methods like res.json(), res.jsonp(), res.send(). This creates an implicit dependency from response.js back to the application's settings, accessed via req.app or this.app at runtime. While not a static circular dependency, it means response behavior is coupled to application configuration in ways that are hard to trace by reading response.js alone.
Recommendation: Document the runtime dependencies on app settings at the top of response.js. Consider whether some settings could be passed explicitly through the middleware chain rather than accessed via the app reference.
medium No TypeScript type definitions in the core package
package.json
The codebase is pure JavaScript with no TypeScript declarations (.d.ts files) bundled in the package. While types exist in DefinitelyTyped (@types/express), having types drift from the actual implementation is a known source of bugs in the ecosystem. The architecture would benefit from co-located type definitions that are verified against the implementation.
Recommendation: Consider adding a types/ directory with hand-written .d.ts files verified by CI, or migrating to JSDoc type annotations that can be extracted to .d.ts files. This would ensure type accuracy and improve the developer experience for the majority of users who use TypeScript.
