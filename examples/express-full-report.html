Performance (6)

medium Synchronous filesystem operations in View constructor ▶
lib/view.js
The View constructor in lib/view.js uses synchronous filesystem lookups via `this.lookup(fileName)` which internally calls `fs.existsSync()` (through the `resolve` method). In production with many concurrent requests triggering view rendering, synchronous filesystem calls block the event loop and degrade throughput. Each render call must stat the filesystem synchronously before it can proceed.
Recommendation: Consider caching resolved view paths after the first lookup. Express does have a `view cache` setting, but the initial resolution per unique view is still synchronous. A pre-warming mechanism or async resolution path would help high-concurrency scenarios.
medium Linear route matching — O(N) per request through all registered routes ▶
lib/application.js
Express's router iterates through all registered routes/layers sequentially for every incoming request. There is no trie, radix tree, or hash-based lookup optimization. For applications with hundreds of routes, each request must linearly scan through layers until a match is found. This is a well-known architectural limitation of Express.
Recommendation: For applications with many routes, order routes from most-frequently-hit to least-frequently-hit. Consider grouping routes under sub-routers to reduce the search space. For extreme cases, consider frameworks with trie-based routing (e.g., Fastify, find-my-way). This is an architectural choice in Express that is unlikely to change in v4.
medium Static file serving delegates entirely to serve-static with no built-in memory cache ▶
lib/express.js
Express's static file middleware (`express.static`) re-exports `serve-static` which reads from disk on every request (relying on OS-level filesystem caching). There is no built-in in-memory cache for frequently requested static assets. For high-traffic applications serving many small static files, this results in repeated syscalls per request even with `maxAge` set (which only affects client caching, not server-side).
Recommendation: For production deployments, serve static files from a CDN or reverse proxy (nginx, CloudFront) rather than through Express. If Express must serve static files, consider an in-memory caching middleware layer or ensure the OS filesystem cache is warm. Set appropriate `maxAge` and `immutable` options to minimize repeat client requests.
low res.send() performs multiple type checks and transformations on every call ▶
lib/response.js
In `lib/response.js`, `res.send()` has a complex flow: it checks for deprecated signatures (2-argument form), handles argument shifting, detects Buffer vs String vs Object types, performs ETag generation (which hashes the entire body), sets Content-Length by computing Buffer.byteLength for strings, and handles HEAD request body stripping. The ETag computation on every non-trivial response body is particularly expensive for large payloads as it requires hashing the full response.
Recommendation: For performance-critical endpoints serving large bodies, disable ETag generation with `app.set('etag', false)` or use a custom weak ETag function based on content metadata rather than body hashing. Consider using `res.end()` directly for raw responses that don't need Express's processing.
low req.ip and req.hostname re-parse on every access (no memoization) ▶
lib/request.js
In `lib/request.js`, properties like `req.ip`, `req.ips`, `req.hostname`, and `req.protocol` are defined as getters that re-execute parsing logic on every access. For `req.ip` with `trust proxy` enabled, this involves calling `proxyaddr()` which parses X-Forwarded-For headers each time. If middleware or application code accesses `req.ip` multiple times per request (e.g., logging, rate limiting, geo-lookup), the parsing work is repeated.
Recommendation: Cache the result of these getters on the request object after first computation (lazy memoization pattern). For example: `get ip() { if (this._ip !== undefined) return this._ip; return (this._ip = computeIp()); }`. Application-level workaround: store `req.ip` in a local variable when accessing multiple times.
